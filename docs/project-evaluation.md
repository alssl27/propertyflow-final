# PropertyFlow project evaluation

**Assisted draft updated 27 October 2026 for learner review.** This evaluation is based on the supplied project, implemented source and recorded test evidence. It is not a first-person account of the learner's experiences. The learner should review the conclusions, correct anything they disagree with and use only claims they can explain and support. No assessor approval or grade is implied.

Live application: [PropertyFlow](https://propertyflow-final.vercel.app). Source and evidence: [alssl27/propertyflow-final](https://github.com/alssl27/propertyflow-final).

## Purpose and outcome

PropertyFlow addresses a coherent front-end problem: a small property-management team needs to connect property records, repair work and certificate dates while seeing current priorities. A shared property ID lets the interface link records and calculate summaries consistently. Compared with disconnected lists, this reduces repeated entry and makes the effect of an edit visible across views. This is a reasoned design justification; no independent customer research or measured business benefit has been recorded.

The implemented prototype provides six working views: Overview, Properties, Repairs, Compliance, Reports and Settings. Property, repair and certificate creation and editing, combined filters, repair status progression, persistent data, CSV export and confirmed reset are implemented and exercised by the recorded tests. The project therefore demonstrates meaningful interaction rather than a static dashboard. Its usefulness is limited to an educational browser workspace containing fictional records. It does not yet support secure, shared business operations.

## Design evaluation

The navigation groups closely related tasks and keeps the overview available as a stable starting point. Summary metrics appear before detailed records, while attention items and shortcuts lead to operational actions. Repeated table, button, card and form patterns make the six views consistent. Text accompanies status colours, giving users an explicit meaning for a condition. Local fonts avoid an external font request. The [UX rationale](ux-rationale.md) and [UX design](ux-design.md) explain these decisions.

On narrow screens, the sidebar becomes a disclosure and wide tables scroll within labelled regions. Recorded browser checks cover all six routes at 320, 375, 768, 1024 and 1440 pixels. Keeping tables preserves the relationship between column headings and values, but users on small screens may need horizontal scrolling. A future study should compare this pattern with a compact record layout using representative tasks. The existing responsive evidence shows rendering and operation in the tested browser viewports; it does not establish real-device touch usability.

Accessibility support includes a skip link, landmarks, associated labels, described field errors, visible focus, live feedback, native dialogs, inert hidden navigation and reduced-motion styling. The initial browser run found dialog-focus, ARIA and contrast problems, which were corrected and retested. This gives stronger evidence of an iterative process than a claim that the first implementation was already accessible. Automated axe results and scripted keyboard checks remain limited to the recorded states. Native browser zoom at 200%/400% was subsequently reviewed in [manual-accessibility-review.md](manual-accessibility-review.md). Screen-reader speech, actual operating-system contrast settings and independent participant usability still need direct evidence. Consult the current [submission checklist](final-submission-checklist.md) and any later accessibility report before making a final claim.

The [wireframe](ux-wireframe.md) is explicitly retrospective. It documents the implemented structure and should not be presented as proof that those artefacts existed before development.

## Code and data integrity

The project retains custom HTML, CSS and vanilla JavaScript modules. Separating `app.js` for presentation and events, `domain.js` for pure rules and `api.js` for loading and persistence makes the responsibilities easier to explain. Pure validation, calculations, date rules and CSV encoding can be tested without a browser. Event delegation allows controls generated by later renders to use a common handler.

Validation exists at both the form and saved-workspace boundary. This protects the application when stored data is damaged or a write is attempted outside a normal form path. The register normalises address and postcode identity to detect duplicates. Related repairs and certificates prevent property deletion. Reports handle empty collections without division by zero, and exported CSV values are escaped and protected against spreadsheet formula interpretation. The postcode rule checks a UK-style format; it does not prove that an address exists.

There is a trade-off in rendering HTML strings inside a central UI module. Escaping user values and keeping pure rules separate reduce immediate risk, but `app.js` combines several views and workflows. If the application grew, splitting view rendering and shared form behaviour into smaller modules would improve maintainability. A framework is not necessary to achieve that separation and would add complexity beyond the present prototype's scope.

## Asynchronous design

Initial JSON requests run together through `Promise.all`. Response status and schema are checked, and a shared `AbortController` cancels pending work after failure or the fifteen-second timeout. Loading, retry and recovery are visible to the user. `Promise.all` preserves the order of its input results; it does not by itself cancel outstanding requests. The service implements that cancellation explicitly.

A service queue orders calls within one tab. In browsers with IndexedDB, each mutation reads, validates, changes and writes the complete workspace inside one `readwrite` transaction. IndexedDB serialises those transactions across tabs, avoiding the lost-update race found when separate contexts used cached localStorage snapshots. Web Locks add ordering for cooperating callers. A best-effort localStorage mirror supports migration and change notifications; environments without IndexedDB use the earlier queued localStorage fallback. Reset validates downloaded replacement data before replacing the authoritative record, and a rejected queued operation does not prevent later operations from running.

The UI uses sequence guards to reject obsolete loads and delayed search work. Search is a local 180-millisecond debounce, not a remote API request. These distinctions are documented accurately in the [learner handover](learner-handover.md).

The approach is appropriate for the static assessment prototype, but it is not a shared server database. Browser data is tied to one profile and origin, can be cleared, is not encrypted or backed up by the app, and has no field-level conflict interface for edits to the same record. The localStorage fallback protects only cooperating code and should be used from one tab. IndexedDB supplies cross-tab transaction isolation for the supported browser path, not multi-user synchronisation between devices.

Unit/service tests cover precise edge cases and controlled timing. Browser tests establish that the UI connects those rules into observable workflows. The HTTP/hash checks separately verify delivery of the intended release. Using these layers gives complementary evidence, but passing them does not prove every device, browser, accessibility mode or possible interaction has been tested.

The current local IndexedDB revision has a complete passing local run. Its production deployment/browser/hash rerun remains pending; the older deployment row must not be used to claim that the new runtime is already verified online.

The [bug report](bug-report.md) documents concrete before/after changes. Three particularly valuable improvements were replacing invented financial graphics with calculations from current records, preventing lost updates and making reset failure-safe. Their value is data honesty and reliable user control. Dialog-focus and contrast fixes show how rendered-browser testing changed the implementation. Initial failure reports and genuine screenshots remain available rather than being replaced with a successful-looking narrative.

## Overall judgement

Within the documented automated scope, PropertyFlow is a coherent and functioning educational front-end prototype. Its strongest evidence is the relationship between documented user stories, real interactions, defensive service rules, genuine failures and retests, and a verified public deployment. The main remaining uncertainty concerns human usability, learner understanding and the applicable course policy. Those cannot be inferred from automated passes or a polished interface. The project should be assessed against the supplied [criteria matrix](assessment-criteria-matrix.md) and the institution's confirmed specification, with any outstanding items stated accurately.
