# Testing methodology

Tests were executed during this revision on 12 October 2026. Source inspection established defects first; unit/service tests verified business rules; actual Chrome browser tests then found and retested UI defects. The initial failed browser report is retained, alongside final results and screenshots. This is current evidence, not reconstructed past development activity.

## Appropriate automation

Node's built-in runner checks deterministic calculations, date boundaries, validation, CSV escaping and persistence failures. Dependencies such as localStorage and fetch are replaced with controlled test doubles to produce malformed JSON, quota failures and overlapping operations reproducibly. These tests are fast and isolate business rules; they do not prove browser rendering.

Playwright drives installed Chrome through the real static server. It submits forms, reloads to check persistence, tests history and keyboard focus, downloads a real CSV, delays or fails JSON requests, and edits from two tabs. axe-core checks all six views at 320, 375, 768, 1024 and 1440px, plus the property dialog. Screenshots are generated by the browser, not by image generation. Browser plugin was not available; the testing skill's regular Playwright path was used.

ESLint checks JavaScript; html-validate checks both static HTML documents; CSS Tree parses CSS and validates supported property/value grammar. CSS custom property substitutions require the browser, so this is not a claim of a W3C CSS-service pass. Prettier checks formatting. A local link checker verifies document and asset targets, not external network availability. npm audit assesses development dependencies at the recorded time.

## Appropriate manual testing

Manual checks remain necessary for screen-reader speech, understandable copy, task efficiency, physical touch devices, browser zoom and OS high contrast. A scoped agent-operated [native Chrome 200%/400% zoom review](MANUAL-ACCESSIBILITY-REVIEW.md) is complete; the deployed Edge suite provides separate cross-browser evidence. These records do not establish screen-reader speech, actual OS contrast/touch-device use, Firefox/Safari behaviour or independent learner usability feedback. Automated contrast and ARIA checks cannot guarantee WCAG conformance. Have a learner or peer follow the manual checklist and record their own observations in TEST-RESULTS-TEMPLATE.md; never mark unexecuted work as passed.

## Reproduce

```sh
npm ci
npm test
npm run lint
npm run validate:html
npm run validate:css
npm run format:check
npm run check:links
npm run test:browser
npm run build
```

Use Node 24+ and an installed Google Chrome; versions actually used are in TEST-RESULTS.md. Every browser test has an isolated browser context and fictional records. Test output lives in docs/evidence. No submitted data is sent to a backend. Tests against the deployed origin use separate browser contexts and reports. Set BASE_URL and use playwright.deployed.config.js as shown in DEPLOYED-TEST-RESULTS.md; it disables the local server and saves all screenshots/reports to evidence/deployed, preserving local evidence.

## Interpretation

A pass means that the assertion passed in the named environment, not that every possible use case passed. The failed initial browser run exposed dialog Tab behaviour, low contrast and invalid ARIA. Later passes demonstrate those scenarios were retested. Expected failure scenarios intentionally log a caught load error; these are distinguished from uncaught pageerror events. A subsequent cloud run passed all 14 browser tests plus 13 independent HTTP/hash checks; see DEPLOYED-TEST-RESULTS.md.

## Extended scope

Edge used the full shared browser suite in its own evidence folder. Forced colours/reduced motion were emulated in Chrome and explicitly distinguished from OS/assistive-technology checks. Virtual time advanced the exact 15-second timeout in service tests without adding an artificial delay to the app. The expanded Node total is 24 tests; details and limits appear in ADDITIONAL-VERIFICATION.md.
